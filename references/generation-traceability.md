# 代际比较与追溯

开始新的一代、版本比较或 Promotion 前读。目标：每代留下足够信息，让人能理解发生了什么、为什么改、结果如何、怎么决定。自动化可以降低人工关注频率，不能降低可观察性——即使完全自动运行，证据仍然存在，区别只是人这轮读没读。

## 先看一个真实示例（人工可读 Diff）

场景：法规资讯分析 V4 相对工作版本 V3。

```
## V4 vs V3 · 运行 runs/004

本代改动：新增「同一事件合并」前置规则（prompts/v4.md 第 12–18 行）。
影响范围：6 / 24 case。

变好（3）：case 07 / 11 / 19 —— 同事件资讯正确合并
          （对照 runs/004/产物/，逐条链到原始依据）。
变差（1）：case 14 —— 不同事件被误合并。新关键错误。
表达不同（2）：case 03 / 22 —— 仅摘要措辞变化，无判断差异。

假设验证：部分支持。「合并提升一致性」成立（3 条预期 case 全部命中），
          但规则未覆盖 case 14 的转发场景。

建议人工重点看：case 14（约 1 分钟）。

我的建议：不采用为工作版本 —— 新关键错误未解决。
          下一代表：合并规则加来源排除条件，预期修复 case 14，
          回归其余 23 条。
```

要点：这份 Diff 帮人做决定——改动是什么、好在哪差在哪、假设是否成立、下一步——而不是文件级 diff 的复读。每个结论都链到具体 case 和产物。

## 代际性质

- **探索轮次**（Discovery）：比较「产生了什么新事实、哪个假设被支持或推翻、用户真正关心的标准是否更清楚、下一轮验证什么」。可以比较产物差异，但成功标准未稳时不宣称某代性能更优。
- **正式变化**（Epoch 内）：先记录版本关系（替换 / 增量 / 并行 / 分流 / 实验），再选参照物和比较范围。只有替换式变化默认用 Candidate 对当前工作版本；增量变化重点查新增能力 + 未受影响部分回归。
- **契约变化**：不是普通一代 → 进 Epoch Review，明确哪些历史结果仍可比较。

## 比较链（全程可追）

```
当前定义 / Epoch Contract
→ 方法版本
→ Run Manifest
→ 产物
→ Diff / Eval
→ Evidence
→ 决策
→ 适用的版本状态指针
```

任一环节可以是项目已有文件或外部系统，但记录中必须能定位。

## 每代最小记录

实际运行时创建独立记录，不覆盖上一代；只建本代实际有内容的文件，小型任务可合并为一个 Markdown。

```
运行记录/<run-id>/
├── manifest.json    # run_id、时间、阶段、Epoch、版本关系、参照版本、
│                    #   输入与 Gold/Eval 版本、证据层级与下一检查点、
│                    #   模型与关键配置、产物/Trace/决策路径、运行状态
│                    #   （不写密钥或敏感数据）
├── 产物/            # 或指向已有产物位置
├── 版本差异.md      # 人工可读 Diff（见上方示例）
├── 评测结果.md      # 有正式评测时
└── 决策.md
```

## 证据类型

```
Observation 观察到的现象
→ Evidence 可验证、可追溯的事实
→ Hypothesis 关于原因的解释
→ Intervention 为验证假设实施的修改
→ Evaluation 修改后的比较结果
→ Validated Learning 结果支持、适用边界清楚的经验
```

一次复盘中的猜测不能直接成为稳定经验；Validated Learning 必须指向支持它的运行和 Evidence。

## 证据梯度（六层，不要求每代做满）

1. **运行有效性**：结构、Schema、测试、完整性、错误检查；
2. **固定案例回归**：关键 Case、规则、不变量；
3. **差异复核**：人工或可追溯的自动对比；
4. **专家抽查**：高价值、低置信度或争议 Case 的裁决；
5. **业务 Gold**：按正式口径标注或验收；
6. **生产反馈**：真实使用结果、事故、申诉、业务指标。

低层证据支持继续试验或可逆的工作采用，不冒充高层结论。Gold 贵时允许多代共享一个业务校准周期：每代仍记便宜证据，达到检查点后集中打标。检查点不只按代数——可由累计有效改动、契约变化、关键回归、方向争议、准备发布、运行量阈值、时间周期、用户要求触发。

## 版本状态（三个指针 + 实验）

- **当前工作版本**：迭代默认起点，与风险相称的便宜证据即可更新；
- **最近业务校准版本**：最近经业务 Gold 或等价高可信反馈确认；
- **生产版本**：对外运行，需发布与回滚要求支持；
- **实验 / 并行版本**：仍在比较、只服务特定场景、不准备替换其它版本。

指针可相同可不同；更新一个不自动更新其它。不把「工作采用」写成「业务已验证」。

## 可比性检查（声称优劣前过一遍）

- 属于同一 Epoch；
- Goal / Definition / Metric 语义和关键边界未实质改变；
- 相同证据依据，或差异已声明并限制结论范围；
- 输入分布和运行条件足够可比；
- 没把结构校验和业务质量混为一谈。

尺子变了 → 标记 `epoch_review_required`，不把分数连成趋势。

## 状态变更与 Promotion

任何状态变更前，先说清要变更的是工作 / 业务校准 / 生产哪个指针。

采用为当前工作版本前至少确认：运行和产物有效；证据与声明范围相称；没有不可接受的关键回归；结论能追到 Diff 和 Evidence；变化可逆或已满足人工确认与回滚要求。

标记业务已校准：必须有业务 Gold、明确裁决者或事先接受的等价高可信反馈。进入生产：另满足项目自己的发布、权限、监控、回滚要求。

决策用与项目语言一致的明确状态，例如：`adopted_as_working`、`kept_parallel`、`experiment_only`、`needs_more_evidence`、`business_validated`、`released`、`rejected`、`epoch_review_required`。不强迫已有项目改枚举。V0.1：不自动修改 Gold，不自动更新任何版本指针。

## 一轮结束

更新状态页中的最近运行、版本关系、证据等级、决策、适用指针、人工待办和下一检查点。若本代发现目标、定义或评测尺子需要实质变化：停止普通优化，进入 Epoch Review。
