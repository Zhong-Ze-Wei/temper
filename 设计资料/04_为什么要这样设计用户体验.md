# 为什么「淬炼」必须把复杂性藏起来

## 当前最大风险不是能力不够，而是用户看不懂

一个系统内部可以有：

- Discovery；
- Formation；
- Epoch；
- Candidate；
- Baseline；
- Evidence；
- Regression；
- Promotion；
- Human Gate；
- Project Discovery。

这些概念对设计系统的人非常重要。

但它们不应该成为用户第一次使用的门槛。

如果用户打开以后第一反应是：

> “所以我现在到底要干什么？”

那产品已经失败了一半。

---

## 用户真正想知道的只有几个问题

第一次进入时，用户真正关心的是：

```text
这东西能帮我解决什么？
↓
我这个任务能不能用？
↓
你现在准备做什么？
↓
我要提供什么？
↓
什么时候需要我？
↓
你做完这一轮以后发生了什么？
↓
下一步是什么？
```

这才应该是产品主路径。

---

## 所以「淬炼」应该是“带着用户做”，不是“让用户学习”

错误体验：

```text
请先判断自己属于 Discovery / Eval Building / Optimization
→ 选择轻量 / 标准 / 严格
→ 决定是否建立 Epoch
→ 创建 Candidate
```

正确体验应该更像：

```text
用户：我现在这个任务结果不稳定。

淬炼：
我先看项目。
↓
我发现你现在不是 Prompt 的问题，主要缺稳定评测。
↓
先给我 5 个业务确认过的 Case。
↓
我跑一轮，整理出 3 个真正需要人工判断的问题。
↓
你只确认这 3 个。
↓
剩下的我继续跑。
```

方法论是系统内部使用的。

不是用户的学习成本。

---

## Loop 应该成为产品的“地图”

Loop 不是一个藏在说明文档里的理论图。

它应该是用户始终能看到的当前工作地图。

例如数据分析场景：

```text
现有需求
→ 摸数据
→ 初版指标 / 取数
→ 发现未知口径
→ 找业务确认
→ 更新理解
→ 重新取数
→ 业务评审
```

AI 应用成熟场景：

```text
Baseline
→ Candidate
→ Run
→ Eval + Diff
→ 自动能判断？
   ├─ 是 → AI 继续修改
   └─ 否 → 人工确认
→ Regression
→ Promotion
```

业务流程理解场景：

```text
现有资料
→ 画当前流程
→ 标未知点
→ 找负责人
→ 用真实案例验证
→ 更新理解
→ 再决定有没有资格优化
```

用户看到图，就应该立即知道：

> **我现在在哪、系统在干什么、下一步去哪里、什么时候轮到我。**

---

## 复杂机制应该逐层暴露

首页只暴露：

- 当前问题；
- 当前 Loop；
- 当前状态；
- 需要用户做的事情；
- 下一步。

只有用户点击“为什么”时，再展开：

- 为什么进入这个阶段；
- 为什么需要 Epoch；
- 为什么 Candidate 还不能晋升；
- 当前 Evidence 到什么等级；
- 为什么某个问题必须人工裁决。

这叫：

> **progressive disclosure（渐进披露）**

复杂性仍然存在，但不会阻塞第一次成功体验。

---

## 产品原则

### 复杂度在后台，行动在前台

用户不需要知道系统如何推理全部状态。

用户需要知道：

> 我现在应该做什么。

### AI 自己能获得的信息，不应该让用户重复提供

先读：

- README；
- 项目定义；
- 数据说明；
- 当前方法；
- 最近运行；
- 评测；
- Git / Markdown。

只有无法从项目中发现、而且会改变方案的问题，才问用户。

### 人只处理高价值信息缺口

不要让人充当：

> 每轮结果检查器。

应该让人只处理：

- 业务事实；
- 目标冲突；
- Definition 变化；
- 风险裁决；
- AI 无法验证的争议。

---

## 一句话 UX 目标

> **用户不需要理解 Loop Engineering，但始终能理解：现在发生了什么、为什么轮到我、我确认以后系统会继续做什么。**
