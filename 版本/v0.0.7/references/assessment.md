# 状态判断与循环强度

在创建结构或修改方法前，用本参考判断任务是否值得持续迭代、当前缺少什么，以及需要多少控制。不要把多个维度压成一个貌似精确的总分；逐项给出结论、证据和不确定性。

## 适用性 Gate

以下多数成立时，建议直接完成任务，不初始化 Temper：

- 一次性工作或普通问答；
- 完全确定性的转换；
- 人工几分钟即可稳定完成；
- 不需要未来版本比较；
- 没有持续学习价值；
- 建立反馈和留痕的成本明显高于潜在收益。

判断问题：下一次遇到同类任务时，这次留下的证据是否会使结果明显更好？如果不会，不建立 Loop。

## 诊断维度

### 目标清晰度

检查是否能回答：

- 谁使用结果，支持什么决定或动作；
- 输入、输出和范围边界；
- 什么算完成或可用；
- 哪类错误最重要、取舍是什么；
- 哪些内容仍只是工作假设。

目标不必一开始完整。若这些问题尚不清楚，应通过真实案例或最小 V0 学习，而不是假装已经冻结正式标准。

### 反馈质量与成本

可信反馈至少应尽量满足：

- 能追到具体 Case 和原始依据；
- 可重复计算，或有明确的人工裁决者；
- 衡量的确是任务价值，而不只是格式正确；
- 同一轮版本比较期间含义稳定；
- 能识别关键回归，而不只给平均分。

结构校验、AI 自评、单次主观观感都可以是信号，但不能单独证明质量提升。

同时检查反馈的成本、延迟、覆盖面和可获得频率。可靠不等于必须每代执行：昂贵 Gold 可以按批次或风险触发，便宜证据负责日常筛错。若只有低成本代理信号，应明确它能证明什么、不能证明什么。

### 版本关系

判断本次变化是：

- 替换：新方法准备取代旧方法；
- 增量：在原方法上增加可选或局部能力；
- 并行：多个方案继续共存；
- 分流：不同输入或场景使用不同方案；
- 实验：只验证假设，暂不进入工作版本；
- 契约变化：目标、边界或评测尺子发生实质改变。

版本号递增不代表必然替换。契约变化通常需要 Epoch Review；其它关系在同一 Epoch 内按受影响范围比较。

### 人工参与与运行节奏

检查任务运行和修改有多频繁，以及人适合在哪里参与：每代复核、抽样复核、周期检查点、异常介入、发布 Gate，或多种组合。记录用户已表达的偏好，不以“鼓励参与”为理由强迫每代做昂贵人工工作。

### 风险与可逆性

检查错误成本、外部影响、规模、可回滚性、权限、合规、安全和人工复核成本。高风险或不可逆是严格控制的硬触发，不代表必须使用复杂 Graph。

### 项目成熟度

检查是否已有：

- 可重复运行的 V0；
- 当前方法或 Baseline；
- 当前工作版本、最近业务校准版本和生产版本是否有区别；
- 可版本化的输入和产物；
- Trace 或运行记录；
- Eval、Gold、Regression 或外部反馈；
- Candidate 与正式版本的区分。

## 阶段判断

选择当前主要阶段，不要求项目永久停留在某一阶段。若不同能力或子任务明显处于不同阶段，给出主阶段并标明局部分支，不把整个仓库压成一个状态。

### Discovery

目标、边界或真正问题仍模糊。重点是形成当前理解、未知项和学习问题，通过案例或最小产物获得证据。此时可以有代际记录，但不要宣称性能版本已经可比。

### Formation

目标已经足够支持行动，但还没有可重复运行的 V0。重点是建立最小任务框架和第一份可观察产物，而不是完整 Eval 平台。

### Eval Building

任务能运行，目标相对清楚，但缺少可信后验。运行与建设 Case、Gold、Regression、可验证指标或人工反馈机制并行。

### Optimization

有可重复工作版本和足够证据支持持续比较。围绕版本差异、诊断、回归、证据积累和适当的校准检查点工作；不要求每一代都有昂贵 Gold。

### Stabilization

任务已进入高频、生产或高风险使用。重点是关键回归、审计、回滚和有限人工 Gate，而不是继续无限增加流程节点。

## 循环强度

阶段回答“现在缺什么”，强度回答“需要多少控制”，策略回答“怎样迭代”。三者分开判断。严格控制不等于频繁 Gold，昂贵反馈也不自动等于严格流程。

### 轻量

适用于低风险、可回滚、探索性强或规模小的任务。通常只需要当前理解、一次运行、观察、一个最小修改和重跑记录。

### 标准

适用于重复任务、需要版本比较、已有或正在建设稳定反馈的项目。至少明确 Epoch、版本关系、当前工作版本、评测依据、人工可读 Diff、Regression 和状态变更规则。

### 严格

适用于高风险、不可逆、生产、强审计或重大错误成本。按实际风险增加 Baseline Lock、关键样本、完整 Trace、人工裁决、风险 Gate 和回滚；不要因此默认引入多 Agent 或复杂 Runtime。

硬规则：出现生产外部写入、合规/安全责任、不可逆结果或重大业务损失风险时，至少采用严格风险控制，即使任务仍处于 Discovery。

## 诊断输出

向用户提供紧凑的诊断卡：

```text
是否值得迭代：是 / 否 / 暂不确定
当前阶段：...
推荐强度：轻量 / 标准 / 严格
局部阶段：...（仅在需要时）
关键依据：...
已有资产：...
主要缺口：...
策略关键因素：反馈成本 / 版本关系 / 人工节奏 / 风险
当前不应该做：...
最小下一步：...
需要人工决定：...
```

不要为了遵守模板重复用户已经知道的信息。每个判断尽量引用项目中的真实文件、运行或案例。
