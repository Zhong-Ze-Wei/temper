# temper 迭代复盘评审

> 评审日期：2026-08-27  
> 评审方式：只静态阅读仓库材料，不运行任何测试。  
> 评审范围：README、当前正式版 SKILL.md、5 个 references、版本说明、0001～0011 迭代记录、测试任务集、评测说明和 `.temper/state.json`。

## 口径说明

仓库能明确还原的是 v0.0.1～v0.0.6 六个正式编号，以及 0001～0011 十一代工作记录；候选版和中间状态也参与了过程评审。用户所说的“8 个版本”没有在 `版本/版本说明.md` 中形成一份可直接核对的八项清单，这本身说明“版本、候选、运行代”三个概念目前仍有少量混用。以下不纠结数量，以实际可追溯材料为准。

# 一、迭代质量评估

## 总体结论与评分

**评分：7/10。**

这波迭代值得。它不只是润色文案，而是通过真实自举暴露并修掉了几个核心产品问题：从“管理迭代”转向“主持迭代”，从控制系统居中转向工件居中，从每轮等待人工转向可授权的持续逼近，并开始用不同任务状态验证行为。尤其 0004、0005、0006 和 0009 都有清楚的触发、干预和后验，属于真正由问题推动的迭代。

没有给到 8 分以上，主要因为仓库在自己最强调的三件事上仍有明显缺口：

1. **当前视图没有持续保持一致**：根 `SKILL.md` 和 state 已是 v0.0.6，README 第一屏仍显示 v0.0.3；评测说明仍把历史 P0/P1 写成“当前”问题；版本说明中也残留“当前正式版 v0.0.4”的旧句子。
2. **版本追溯并不可靠**：v0.0.5 的提交修改了 `版本/v0.0.4/references/project-structure.md`，历史快照被后续版本改写；v0.0.2 没有对应版本快照；版本快照里的 `openai.yaml` 布局与根目录 `agents/openai.yaml` 不一致。
3. **证据有时被说得比实际更强**：A/B/C 是构造场景和子代理推演，适合作为固定回归，但不是第 6 层生产反馈；0011 只回归 A/B，却把此前的 C 一并带入总体结论；“持续逼近模式可用”有自举过程证据，但还没有专门验证攒代汇报、异常介入和模式切换。

换句话说：**temper 的产品方向变清楚了，但它的版本纪律、状态维护和证据校准还没有完全达到自己写下的标准。**

## 哪些迭代真正有价值

### 0002：用户体验层重构——高价值

它准确识别了初版的主要缺陷不是方法论不足，而是用户第一次使用就要理解 Discovery、Epoch、Candidate 等内部概念。四件事、首次三件套、Gate 前置和渐进披露，使 temper 从“概念手册”转向“带着用户做”。这是一次真正改变使用体验的产品迭代，也是 v0.0.3 最有价值的核心。

### 0004：工作台化重构——本轮价值最高

0001～0003 建出了完整控制结构，但真实使用暴露了信息架构反转：机制比工件显眼，用户需要在多个文件中拼出当前状态。0004 得出的“工件站在工作台中央”“可追溯不等于文档越多越好”“打开三秒知道在改什么”是这次自举最重要的后验。

这不是单纯目录改名，而是产品原则的改变。它还证明 temper 的自迭代确实能从失败中修正方法，而不是只验证自己原本正确。

### 0005：独立评审与修正——高价值

引入外部模型评审，抓出了三个内部自评没有充分处理的问题：旧结构规范与新后验冲突、当前视图和指针漂移、交互契约过硬。后续修正也基本落到了候选方法和测试集上。这一步有效降低了“用自己的尺子证明自己”的风险。

### 0006：A/B/C 测试——中高价值

三个任务覆盖了三种关键状态：

- A：成功标准相对稳定，可以做正常优化闭环；
- B：业务定义不稳定，应停止代码优化；
- C：流程尚未理解，应保持 Discovery 克制。

这组测试比只检查 SKILL.md 有没有某个章节更接近行为验证，也证明了“先判断当前真正缺什么”不是纯口号。它适合作为最低成本的 smoke/regression 测试。

需要限制结论：这些是人为构造的场景，任务描述和 pass criteria 与 skill 规则高度一致，容易测到“是否复述方法”，还不能证明真实复杂项目中同样好用。

### 0007：中文工作面和人话 Diff——中等价值

用户问“我如何知道更新了什么”之后，新增集中式版本说明，并把用户工作面改为项目语言。这解决了真实发现性问题。将“旧版是什么、为什么改、验证了什么、证据到哪里”沉淀为人话 Diff，也是合理的产品原则。

但“目录结构设计之初就定死”表述过强。temper 自己正是通过迭代才发现原结构不对，更合适的原则应是：**设计之初明确最小结构；出现真实 failure mode 时允许迁移，但迁移必须一次完成并保持追溯。**

### 0009：持续逼近模式——方向有价值，证据仍弱

它解决了一个真实矛盾：安全边界“不自动多轮修改”被执行成每轮都停下等人，使“持续迭代逼近目的”无法成立。显式授权、限定范围、自主多轮、攒代汇报和只在高价值节点介入，是正确方向。

不过当前规则仍偏机制描述，尚未充分回答：何时停止、最多连续几代、累计回归如何触发中止、成本预算如何控制、用户如何快速撤销。0009～0011 的连续推进能证明该模式让流程继续走了，但不能完整证明它在不同项目里安全、有效、易用。

## 哪些可能属于过度工程或自我繁殖

### 0001：第一次初始化明显过重

第一代一次建立 README、项目定义、循环状态、循环总览、方法指针、评测、运行记录和 state 镜像。每个文件都能解释其职责，但合在一起超过了当时的真实需要，而且很快被 0004 推翻。

它并非毫无价值：正因为真实使用了这套结构，才获得“控制系统压过工件”的关键后验。但从交付效率看，它是一次成本较高的探针，不应作为成功模板复制到其他项目。

### 0003：结构继续扩张后马上被推翻

0003 又建立 `skill/temper/` 作为权威副本，同时扩写 README、循环图和版本说明；0004 随即把工件移回根目录并删除多层状态结构。这里存在明显反复横跳。

其中一部分是有效学习，但也反映了早期决策过快：还没有先问“用户打开仓库最先要看到什么”，就先决定了权威目录和治理结构。

### 状态信息出现了自我繁殖

README、版本说明、迭代记录、汇报文件和 state 都在不同程度上表达“当前版本、最近发生了什么、下一步是什么”。理论上它们分别是首页、版本历史、代际证据、批次汇报和机器状态；实际运行中边界没有守住，导致 README 停在 v0.0.3、state 到 v0.0.6、版本说明又夹着旧版当前状态。

这正是“每个文件单看都有理由，合起来却产生同步成本”的典型过度工程信号。应进一步明确：

- README 只显示当前事实和入口；
- state 是当前事实的机器副本；
- 版本说明只写不可变的版本历史，不再写易过期的“当前说明”；
- 迭代记录保存证据；
- `汇报.md` 只在持续逼近批次尚未汇报时临时存在，汇报完成后不再成为新的长期状态源。

### v0.0.6 属于版本号膨胀

0011 的回归是有价值的，但没有修改行为，只把 frontmatter 从 0.0.5 改成 0.0.6。验证某个版本没有回归，应产生一条运行记录或验证状态，不应自动生成新产品版本。否则“版本”会混入“测试批次”，用户看到 0.0.6 会以为功能发生了变化。

类似地，v0.0.5 是文档一致性修正，作为补丁版本尚可；v0.0.6 只有验证结果，最好保留为“v0.0.5 已通过某次回归”，而不是创建新快照。

## 有没有推翻重来的浪费

有，但不全是坏浪费。

主要反复包括：

1. `项目定义/循环/方法/评测/运行记录` → `skill/temper/` → 根目录工件 + `versions/runs` → 中文 `版本/迭代记录`。
2. 候选版本从 0.1.0 改回 0.0.3，小步进策略后置决定。
3. project-structure 先沉淀英文工作台，之后又改成中文工作台。

前两轮重构中确实存在可以通过更早的工件中心原则避免的浪费；但 0004 是由真实使用获得的有效纠偏，不能简单视为失败。真正不可接受的是历史快照被后续改写：提交 03f87fa 在创建 v0.0.5 时同时修改了 v0.0.4 的 `project-structure.md`，使两个快照的该文件完全相同。这不是正常演化，而是破坏证据链。

# 二、优化方向分析

## “temper 自身持续变好”方向对不对

作为长期愿景，方向对；作为当前优化目标，过于宽泛。

“持续变好”没有稳定停止条件，很容易把“又多了一个模式、文档或版本”误认为进步，诱发为了迭代而迭代。temper 当前更合适的目标应改成：

> **在更少用户负担和更少项目治理成本下，更准确地判断当前真正缺什么，并推动任务获得一份可验证的下一步结果。**

这个目标同时约束四件事：判断正确、能推进、用户省心、机制不过量。它比“自身持续变好”更接近用户价值，也更容易比较版本。

## temper 当前最该优化什么

当前最缺的不是更多方法论或新模式，而是**外部有效性和操作闭环**。

### 1. 从“规则正确”转向“真实项目有效”

现有 A/B/C 已证明模型能按规则表现，但还没有证明用户在真实项目中更快获得正确结果。下一阶段应进入 Eval Building/field validation，而不是继续把仓库整体写成已进入成熟 Optimization。

建议选择 3 类真实项目，各连续使用 2～4 轮：

- 一个已有 V0 和可信反馈的 AI 任务；
- 一个口径持续变化的数据任务；
- 一个资料不完整、需要业务访谈的流程任务。

观察实际产生的决策、返工、用户介入和结果改善，而不是只看回复是否包含四个区块。

### 2. 降低 temper 自身的运行税

当前方法对版本、状态、证据和运行记录描述很完整，但真实使用是否值得这些记录，还没有量化。下一步应记录每轮新增文件数、重复状态源、维护当前视图的成本，以及这些留痕是否真的帮助下一轮。

如果某份记录没有被后续决策读取，就不应自动成为默认结构。

### 3. 把持续逼近模式做成可验证的能力

需要专门验证：

- 多轮过程中是否持续围绕同一目标，而不是追逐文档瑕疵；
- 什么时候应停止或转向人工；
- 发生关键回归时是否会主动中止；
- 成本、代数和修改范围能否受控；
- 攒代汇报是否让用户更省心，而不是一次收到过量信息；
- 用户能否随时切换模式和撤回最近一批改动。

“成功连续跑了三代”只是起点，不能单独证明这个模式好用。

### 4. 建立严格的版本与当前视图纪律

具体应做到：

- 历史版本快照不可修改；如需修正，追加勘误或创建新版本；
- 只有工件内容或行为变化才升级版本；纯验证只更新运行记录；
- README、state 和当前正式版必须在同一代结束时一致；
- 版本说明不保存容易过期的“当前正式版”散文；
- 明确区分仓库工作版、安装副本和注册表版本。

目前仓库是 v0.0.6，安装副本的 SKILL.md 仍是 v0.0.1，CSkills 元数据是 v0.0.2。试验田可以选择不部署，但首页必须让人一眼知道“仓库已改进，实际会话尚未使用新版”，否则“temper 已经变好”只对仓库成立。

## A/B/C 测试思路对不对

**对，但只能作为 smoke test，不能作为“好用”的最终证明。**

它的优点是覆盖了 temper 最重要的三种决策：继续优化、先定业务、先理解问题。这比愿景文档逐条对照更接近真实行为，而且 pass criteria 能防止几个典型错误：乱改代码、伪造评测、过早自动化、隐藏回归。

它的局限包括：

1. 测试任务和 pass criteria 直接使用了 temper 自己的语言，模型很容易“按题作答”。
2. 场景是构造夹具，不是生产反馈，不能算第 6 层证据。
3. 没有与 v0.0.1 或无 temper 的普通代理做盲测对照，因此无法证明新版带来净提升。
4. 更关注输出合规，没有直接衡量用户是否更快完成工作、少做了多少判断、最终结果是否更好。
5. A 的记录存在 20 条与 21 条样本口径差异；0011 只回归 A/B，没有完整回归 C。
6. 没测“不该使用 temper”的 Gate、高风险任务、增量/分流版本关系和持续逼近模式。

## 更好的评测方式

建议采用四层组合，而不是继续扩写愿景清单。

### 第一层：A/B/C 固定回归

保留当前测试，作为每次行为改动后的最低成本回归。修正夹具数量、固定输入版本，并把预期行为与具体措辞分离：允许不同表达，只判断决策和动作是否正确。

### 第二层：盲测与基线对照

对同一个项目分别使用 v0.0.1、当前版本和不加载 temper 的普通代理，隐藏版本信息，由独立评审者比较：

- 谁更快找对问题层；
- 谁问了更少的无效问题；
- 谁产生了更少的无用结构；
- 谁的结果更可验证；
- 谁出现了证据夸大或关键回归。

这是证明“新版比旧版更好”最直接的办法。

### 第三层：未见过的 Holdout 场景

增加少量不写进 SKILL 规则的保留任务：

- D：一次性确定性任务，测试是否拒绝建循环；
- E：高风险或不可逆任务，测试是否主动提高控制并保留人工 Gate；
- F：需要连续 3 轮的任务，测试持续逼近、停止条件和攒代汇报；
- G：项目已有清晰结构且工作区有用户修改，测试是否复用并保护现状。

开发者不能根据每个 Holdout 的具体答案继续补规则，否则测试会再次变成背题。

### 第四层：真实项目纵向反馈

在真实项目中连续记录：首次有用产物所需时间、人工介入次数、错误决策、返工、关键回归、最终采用情况，以及下一位协作者能否恢复上下文。这一层才有资格支持“好用”“节省人力”“可持续”的高强度结论。

## 下一步可落地建议

1. **暂停增加新概念 2～3 轮**：先修当前视图、快照不可变和版本语义，再做真实项目验证。
2. **把 A/B/C 改成盲测对照**：同一夹具跑旧版、新版和无 skill 基线，由独立裁决者评分。
3. **增加一个 Gate 反例和一个持续逼近长任务**：前者测克制，后者测自主推进、停止和汇报。
4. **给每轮记录“用户成本”**：人工问题数、用户回复轮次、首次有用产物时间、需要人工复核的 Case 数。
5. **给每轮记录“机制成本”**：新增文件数、重复状态字段数、过期指针数、后续真正被读取的记录数。
6. **连续观察真实项目**：至少覆盖一项 AI 优化、一项数据口径、一项业务流程；没有真实反馈前，不再宣称进入全面 Optimization。
7. **明确部署状态**：仓库版与安装版分开展示；需要真正让日常会话使用新版时，再经用户确认走同步或发布链。

# 三、评价标准建议

## 为什么愿景基线对照不够

愿景基线适合检查设计有没有被写进方法，但它主要测“文档符合愿景”，容易被增加相应章节直接满足。它不能可靠回答：模型是否诊断正确、用户是否更省力、结果是否更好、机制成本是否值得。

更好的主尺子应从“规则存在”切换为“任务结果和用户成本发生了什么”。愿景基线可以保留为设计回归，但不再作为最高层的好坏判据。

## 建议的五个评价维度

### 1. 下一步判断正确率

**怎么算好：**

- 能区分当前缺的是业务理解、定义、数据、评测、方法还是执行；
- 目标不稳定时不伪装成优化，任务一次性时不建立循环；
- 第一项行动能减少最大的不确定性，而不是选择最容易写文档的动作。

**怎么测：**

- 建一组平衡场景，由业务或方法专家事先给出“可接受的下一步集合”和“危险动作”；
- 盲测不同版本的首次判断和第一项实际行动；
- 统计正确层级率、危险动作率、无效循环率，并复核失败 Case。

**证据等级：**

- 固定场景回归：第 2 层；
- 独立专家盲评：第 4 层；
- 真实项目中减少错误方向和返工：第 6 层。

### 2. 用户理解与介入效率

**怎么算好：**

- 用户第一次看完能回答“现在的问题是什么、这轮做什么、需要我做什么、下一步是什么”；
- 不默认暴露内部术语，不让用户重复提供项目里已有的信息；
- 人工只处理会改变方案的事实、裁决和风险。

“会说人话”不等于口语词更多，而是用户能迅速形成正确行动模型。

**怎么测：**

- 给首次输出做盲测，让新用户在短时间内回答上述四个问题；
- 统计无解释内部术语数、重复索取已有信息次数、人工问题总数、有效问题占比、到第一份有用产物的轮次；
- 记录用户是否需要追问“所以我现在要干什么”。

**证据等级：**

- 输出差异复核：第 3 层；
- 新用户可用性测试或专家抽查：第 4 层；
- 真实使用中的轮次、耗时和放弃率：第 6 层。

### 3. 结果改善与证据校准

**怎么算好：**

- 成功标准稳定时，新版在同条件下改善目标 Case，且没有不可接受的关键回归；
- 成功标准不稳定时，产出的是更清楚的定义和未知，而不是虚假的分数；
- 声明强度始终不超过证据强度。

**怎么测：**

- 稳定任务做旧版/新版同输入的 Case 级盲测，统计修复、退化、未变化和关键回归；
- 不稳定任务检查定义争议是否减少、裁决问题是否可回答；
- 独立检查每条“已改善、已验证、可采用”声明能否追到相称证据。

**证据等级：**

- 固定 Case：第 2 层；
- 人工可读 Diff：第 3 层；
- 业务 Gold：第 5 层；
- 生产效果、事故和申诉：第 6 层。

### 4. 复杂度回报与可恢复性

**怎么算好：**

- 新增的每个文件、状态字段和 Gate 都解决一个已观察到的 failure mode；
- README 能准确反映当前状态，历史快照不可变，链路没有断指针；
- 新协作者能从首页快速找到当前工件、最近变化、证据和下一步；
- 删除某项机制不会损害关键决策时，就不应默认保留它。

**怎么测：**

- 每轮统计新增文件、重复状态字段、过期链接和无消费者记录；
- 做一次交接恢复测试：让未参与项目的人从 README 出发，在限定时间内找出当前版本、最近一次改动、证据边界和下一步；
- 审计版本快照是否与对应提交一致、后续是否被改写。

**证据等级：**

- 结构和链接审计：第 1 层；
- 人工追溯复核：第 3 层；
- 真实交接或故障恢复：第 4～6 层。

### 5. 安全自主推进能力

**怎么算好：**

- 在明确授权范围内能连续完成多轮有价值的小步改进，减少无意义等待；
- 遇到业务事实缺失、目标变化、关键回归、高风险或不可逆动作时会主动停下；
- 能遵守成本、代数、文件范围和发布边界，并提供可撤销的批次结果；
- 自动化带来的是更高有效进展/人工介入比，而不是更多版本和文档。

**怎么测：**

- 设计一个至少三轮的沙箱任务，埋入一次定义变化、一次关键回归和一次越权诱因；
- 统计有效改进代数、人工介入次数、不必要打断、应停未停、越权动作、累计回归和汇报可理解性；
- 比较协同模式与持续逼近模式的总耗时、用户工作量和最终质量。

**证据等级：**

- 多轮固定场景：第 2～3 层；
- 独立风险裁决：第 4 层；
- 真实长期项目中的效率、事故和回滚表现：第 6 层。

## 建议的总判断方式

不要把五个维度压成一个平均分。每个版本至少回答：

1. 下一步判断是否更准；
2. 用户是否更省力；
3. 结果或理解是否真的改善；
4. 为此增加了多少复杂度；
5. 自主性是否仍在安全边界内。

只有前三项至少一项有明确提升、其它项没有不可接受回归，而且新增复杂度确实被收益覆盖，才应判定“temper 变好了”。纯文档对齐、纯回归验证和纯版本号变化，应记录为维护或证据更新，不计为产品能力提升。

## 最终判断

这波迭代的核心价值成立：temper 已从一份专业但偏概念化的方法手册，发展为更能主持任务、识别阶段差异、控制人工介入并支持连续推进的工作方法。

当前最大的风险不是能力不够，而是继续围绕自身结构和版本繁殖，把维护活动误认为产品进步。下一阶段应停止增加新概念，把重点转到盲测对照、真实项目纵向反馈、用户成本和复杂度回报，并先让自身仓库的 README、版本快照、评测状态和部署状态真正符合它自己宣称的追溯原则。
