# 版本说明

> 每个版本改了什么，一眼看懂。这是"两版差异"的唯一入口；各代运行细节在 `迭代记录/`。

## 版本号规则

- **小步进**：每改一点 +0.0.x（0.0.2 → 0.0.3 → …），不搞大跳。
- **唯一版本号**：SKILL.md frontmatter 的 `version` 字段。
- 版本只反映"改到哪了"，不承诺外部发布。本仓库是试验田，不主动同步 GitHub / CSkills / 安装位置。

## v0.0.4 → v0.0.5 改了什么

### 一句话

**方法文档里给的默认目录形态，和自己的仓库长成一样了** —— 修掉"文档一套、项目一套"的脱节。

### 为什么改

持续逼近第一波检查发现：`references/project-structure.md`（正式版方法）里的标准形态示例还写着 `versions/`、`VERSION.md`、`runs/`，但真实仓库已经用 `版本/`、`版本/版本说明.md`、`迭代记录/`。方法文档和自己的真实形态脱节，违反"用它自己"的一致性。

### 改了什么

- `references/project-structure.md` 标准形态示例改为**真实验证过的中文工作台形态**（版本/ + 版本说明.md + 迭代记录/ + state.json）。
- 新增"命名约定"（用户工作面中文、技术内部可英文）和"一致性规则"（文档形态必须与真实项目一致）。
- README 目录导航修正残留的"v0.0.3-候选"。

### 证据

- 一致性修正：方法示例 = 真实仓库形态（本仓库即活例）。
- 这是文档/示例修正，不改行为，风险低。

### 一句话

### 为什么改

晋升 v0.0.3→0.0.4→0.0.5 后，正式版路径变了（references 换过、加了持续逼近模式），需要确认行为仍与候选一致。这也是对"持续逼近模式"这个新机制本身的第一次真实验证。

### 改了什么

- 无行为改动，仅验证。

- 结果：A 正确做最小修复（3 个标注错误案例确定性修复、0 退化、诚实标注推演边界）；B 正确识别业务口径缺口 + 克制住不改代码 + 新发现 first_order_date 语义污染。
- 行为与候选版一致 → 晋升没破坏东西。

### 证据

- A/B 行为回归通过（第 1-2 层证据：规则一致性 + 固定案例回归）。
- ⚠️ 仍是规则推演 + 单次执行，非长期生产反馈；#6/#18 等旁支变化需真实复跑确认。

## v0.0.6 → v0.0.7 改了什么

### 一句话

**temper 现在会自动载入新的评测基准，而不是等用户问"你载入没有"。**

### 为什么改

用户发现 Cognitive Walkthrough 被加进了测试集文档，但 temper 自己"不会自动载入它"。根因：temper 知道"要评测"，但不知道"评测基准本身是活的、要被迭代的"。

### 改了什么

- `SKILL.md` 新增"评测自动载入"机制：每次迭代把评测当被测对象，遇到新的可判定标准 → 判断有效性（可判定/覆盖盲区/证据可标注）→ 有效则纳入测试集、无效则说明原因。
- `评测/评测说明.md` 重写为完整评测体系（愿景对照 + 真实反馈 + 行为测试集 + 认知走查四维），并明确"评测自动载入"是机制而非约定。

### 验证 / 证据

- 机制性改动：加能力，不改既有行为。
- 直接解决了用户指出的 failure mode：新评测基准（如 CW）会被自动识别并纳入，而非依赖用户提醒。
- ⚠️ 尚未验证"它真的会自动载入"——需要一个新评测标准来测这条机制本身。

## v0.0.3 → v0.0.4 改了什么

### 一句话

**temper 从"等你验收才动"变成"可以自己连续跑几轮，攒着一起给你看"** —— 它具备了持续逼近目的的能力。

### 为什么改

真实使用暴露：temper 边界里"不自动多轮修改、不自动 Promotion"本意是安全阀，结果成了枷锁 —— 每一轮都停下等人，无法"持续迭代逼近目的"。用户要求打破它。

### 改了什么

| 改动 | 位置 |
| --- | --- |
| SKILL.md 版本边界新增"持续逼近模式"：自主多轮 + 攒代汇报 + 人工只在三处介入 | SKILL.md |
| interaction-contract.md 新增"持续逼近模式下的交互差异"（每代不打扰、攒代汇报、中途只找三件事） | references/interaction-contract.md |
| 新增 `迭代记录/汇报.md`：攒代汇报的累积文件 | 迭代记录/ |
| 版本号 0.0.3 → 0.0.4 | SKILL.md frontmatter |

### 验证 / 证据

- 这是机制性改动（新增能力，不改动既有行为），默认仍走人机协同，持续逼近模式需显式触发。
- 逻辑自洽：SKILL.md 主边界 + interaction-contract 细节 + 汇报文件三者一致。
- ⚠️ 尚未用真实"持续迭代"任务验证该模式是否真的好用 —— 待下一波持续逼近时检验。

## 版本怎么升

- **任何改动**（行为、文案、机制微调）→ 小步进 +0.0.x
- **"什么叫做好"变了** → 契约级变化，记一次 Epoch Review，版本仍小步进
- 不搞 0.1.0 这种大跳，除非明确到了"方向级重做"

## 怎么发一版（试验田纪律：不主动同步）

```text
改 版本/<新版本>/ 里的 SKILL.md（或根 SKILL.md）
  → 验收
  → 同步到安装位置 ~/.agents/skills/temper
  → cskills publish <含 SKILL.md 的目录>  （发到注册表）
  → cskills sync                        （拉回，保持两边一致）
```

发布是**外发动作**，必须你点头才做。本地仓库只是试验田，**不主动**同步 GitHub / CSkills / 安装位置。

## 两个"temper"别搞混

## v0.0.2 → v0.0.3 改了什么

### 一句话

**从"概念手册"变成"带着用户做"**：用户不再需要先学 Discovery、Epoch、Candidate 这些术语，打开就能知道现在在改什么、要不要自己、下一步去哪。

### 旧版（v0.0.2）是什么

- 开篇是"核心原则 + 工作方式 1-6"，需要用户先理解内部流程才能配合。
- 首屏直接输出诊断卡（阶段/强度/策略/版本关系），概念直接暴露。
- 用户面对话无固定契约；没有"该不该用 temper"的前置判断。
- 结构是抽象的"逻辑职责"描述，没有给出具体目录形态。

### 新版（v0.0.3）改了什么

| 改动 | 旧版 | 新版 |
| --- | --- | --- |
| 首屏 | 概念手册（工作方式 1-6） | "你只需要知道四件事"（现在什么情况/这轮干嘛/要不要你/做完看到什么） |
| 概念暴露 | 直接输出诊断卡 | 沉到"内部机制（按需展开）"，不阻塞首次体验 |
| 首次对话 | 无固定格式 | 三件套【判断】【计划】【需要你】 |
| 每轮交付 | 无约定 | 默认四样：结果/差异/证据/待你确认 |
| Gate 前置 | 只藏在 references | 首屏"该不该用淬炼"一句话判断 |
| 人机分工 | references 有支撑 | 职责边界表显式化 |
| 打扰节奏 | 无 | 默认一轮 2 次（开始+结束），异常即时 |
| 交互契约细节 | 无 | 新增 `references/interaction-contract.md` |
| 结构规范 | 抽象职责 | 工件中心工作台（README + 版本/ + 迭代记录/ + state.json） |

### 为什么改（依据）

- 真实使用（第一轮自举）暴露：temper 会"管理一次迭代"但不会"主持一次迭代"，机制层比用户工作面完整，一进来全是内部术语。
- 设计文档（设计资料/04）本就要求：复杂度在后台、行动在前台、progressive disclosure。
- codex 独立评审确认方向对，并修正了三类问题（结构规范冲突、指针漂移、契约过硬）。

### 测试验证了什么（评测/测试任务集.md）

三个真实任务 A/B/C 全通过：

- **A 客服分类**：正常优化闭环成立（V0→diff→最小修改→复验→诚实边界）。
- **B 新增客户口径**：识别出缺的是业务口径不是代码，克制住不改代码不造评测。
- **C 报销流程**：进入 Discovery，克制住不给自动化方案，暴露未知。

三个任务里，术语（Discovery/Epoch/Candidate）只出现在内部推理，**没有暴露给用户** —— 证明"内部机制按需展开"真实生效。

### 证据能支持到什么

- ✅ 用户体验层重构方向正确，三个真实任务里行为符合愿景。
- ✅ 首次交互不再吓退用户。
- ⚠️ 仍缺：真实长周期使用反馈（生产反馈层）；interaction-contract 的"默认 2 次打扰"在复杂任务里是否够用。
