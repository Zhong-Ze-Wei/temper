# 从真实场景看「淬炼」为什么成立

「淬炼」不是从一个抽象框架倒推出来的。

它来自多个真实工作场景里反复出现的同一类问题：

> **任务一开始并不知道完整正确答案，但可以通过真实运行和反馈不断逼近更好的状态。**

---

# 场景一：AI 应用

例如一个法规资讯分析任务。

第一版已经能跑：

- 判断相关性；
- 合并事件；
- 生成解读；
- 做影响分析；
- 给建议动作。

但跑起来以后出现：

- 合并不稳定；
- 某些相关性判断错误；
- 影响分析依赖业务背景；
- Gold 不完整；
- Prompt 改了以后，不知道新版本是不是整体更好。

这时自然形成：

```text
当前方法
→ 跑真实任务
→ 结果
→ Diff
→ 找系统性问题
→ 修改方法
→ Regression
→ 再跑
```

同时又有两条反馈：

```text
业务打标：这一版本身对不对？
版本 Diff：这一版相对上一版改变了什么？
```

这就是最初的 Loop 来源。

---

# 场景二：数据分析

数据分析的情况更加说明：

> 产品不能只服务“已有明确目标的 AI 优化”。

真实工作可能是：

```text
先出一个大框架
→ 补内容
→ 发现数据不对
→ 查来源和结构
→ 发现口径不确定
→ 多种方法验证
→ 根据业务逻辑判断
→ 形成产物
→ 找业务开会拉通
→ 业务判断是否符合管理需求
```

这里 AI 能帮助：

- 查已有数据说明；
- 做结构扫描；
- 对比不同取数结果；
- 找异常；
- 总结口径冲突；
- 记录当前假设；
- 生成需要业务确认的问题清单。

但 AI 不能替代：

- 集团里没有数字化记录的软性规则；
- 业务流程为什么这么设计；
- 最终管理需求是否被满足。

所以系统必须允许：

> **AI 自动消费已有信息，人提供系统里不存在的事实。**

这也是为什么人不是“失败兜底”，而是反馈系统的一部分。

---

# 场景三：业务流程

还有一种情况更加极端：

> 我们甚至还没搞懂流程为什么这样。

这时谈“优化流程”本身就是错误的。

正确工作应该先是：

```text
读取现有资料
→ 画出当前理解
→ 标出不知道的节点
→ 找实际负责人
→ 用真实 Case 验证
→ 修改流程理解
→ 再确认
```

只有当能够回答：

- 谁在做；
- 为什么做；
- 输入是什么；
- 输出是什么；
- 哪些异常重要；
- 管理目标是什么；

才有资格进入：

> “怎么优化”。

因此「淬炼」需要能够识别：

> 当前任务不是 Optimization，而是 Discovery。

---

# 三个场景共同抽象出了什么

## 任务的真实状态比工具选择更重要

不是一上来问：

> 用什么 Agent？

而是先问：

> 当前真正缺的是业务理解、评测、数据、方法，还是执行能力？

---

## 后验反馈必须能改变下一轮

如果每次运行以后只是：

> 看一眼结果。

但没有形成：

- Evidence；
- Problem；
- Hypothesis；
- Change；
- Validation；

那么运行再多次也只是重复消耗。

---

## 人机边界是动态的

早期：

```text
AI 跑
→ 人全部看
```

中期：

```text
AI 跑 + 自动 Diff
→ 人只看重点
```

成熟：

```text
AI 自动 Run / Eval / Regression
→ 争议和目标变化才找人
```

所以人的参与方式不应该和控制强度混为一谈。

---

## 需求也可以在运行中成熟

很多真实需求不是：

> 业务一开始写清楚 → 技术执行。

而是：

```text
有一个模糊问题
→ 做出第一个东西
→ 业务看见以后才知道自己真正需要什么
→ 再修改
```

所以「淬炼」支持从：

> 模糊想法

开始，而不是要求一开始就拥有完美 Goal / Metrics / Gold。

---

# 最后得到的产品定义

这些场景最终指向的是同一个产品：

> **从一个模糊想法或还不稳定的任务开始，先理解当前现实，再建立刚好足够的行动框架；让业务理解、数据口径、任务定义、方法和评测在真实产物与反馈中逐渐成形；AI 能判断的部分逐渐自动化，人只在真正需要外部事实和裁决的地方介入，直到形成当前稳定可信的方法。**

这就是为什么我们要做「淬炼」。
