# 0012 · Cognitive Walkthrough 走查（4 种状态）

## 方法

用户建议用 Cognitive Walkthrough 测试 temper：对每个交互步问四问（用户知道要做什么吗 / 知道为什么吗 / 有没有明确反馈 / 能理解下一步吗）。任一"不知道"则该步失败。

## 做法

用正式版 v0.0.6 对 4 种项目状态各做一次首轮走查（子代理扮演 temper，读 SKILL.md + references）：
1. 空项目（只有一句 README）
2. 只有目标（没方法没数据）
3. 伪装内容（表面像取数优化，实则是销售口径问题）
4. 正常项目（V0 + 样例）

## 结果：4/4 通过

| 场景 | 四问 | 结论 | 亮点 |
|---|---|---|---|
| 空项目 | 全过 | 合理 | 没凭空造结构，直指目标语义最大不确定性 |
| 只有目标 | 全过 | 合理 | 没急着上方案，先要真实样本拆审阅维度 |
| 伪装内容 | 全过 | 合理 | **看穿伪装**：拒绝改 SQL、拆掉"加去重"直觉、发现 status 字段支线 |
| 正常项目 | 全过 | 合理 | 先建可裁决基线，只问 5 条口径，显式承诺下轮才改 |

## 关键证据

- 场景 3 是判别力最强的：表面"数字不对→改取数"，temper 指出"加去重"对 SUM(amount) 求和口径是负优化、发现 status 字段（退货/取消）这条被忽略的支线、把业务裁决设为唯一门槛。
- 证明"用户面四件事 + 三件套 + 渐进披露"在真实交互里生效，不是文档摆设。

## 发现（收进方法候选）

场景 4 走查自评揭示：**"只读不改"的首轮必须配"你裁决后下轮出 V1 并回测"的显式承诺**，否则用户会卡在"你说了半天到底改不改"。这是"用户已授权迭代时，首轮多久进入实际修改"的边界问题，值得收进 interaction-contract（下一轮考虑）。
