# 0007 · 目录中文化 + 版本说明 + 原则沉淀

## 触发（用户反馈）

1. 用户问"0.0.3 的人话 diff 文档会写在里面吗？我如何知道我更新了什么？"—— 暴露 diff 功能缺失。
2. 用户指出"目录结构是用户体验第一界面，设计之初就该定死"。
3. 用户指出"一开始不是说结构最好都是中文名吗，为什么下面目录几乎都是英文"。
4. 用户追问"这个说明是否应该被沉淀到 temper 中，因为它也是一个方法指导"—— 是，应沉淀。

## 本代改动

| 项 | 处理 |
| --- | --- |
| 顶层目录中文化 | `runs/`→`迭代记录/`、`versions/`→`版本/`、`temper_docs/`→`设计资料/`（git mv 保留历史） |
| 候选目录中文 | `v0.0.3-candidate`→`v0.0.3-候选` |
| 技术内部保留英文 | `references/`、`agents/` 不动（按发布需要） |
| 版本说明 | 新建 `版本/版本说明.md`：时间线 + v0.0.2→v0.0.3 人话 diff + 版本规则 + 发布链 |
| 删旧 VERSION.md | 内容合并进 `版本/版本说明.md` |
| README | "两版差异"入口改指版本说明；导航全部指向新目录 |
| state.json / 评测 / 测试集 | 路径引用全部更新 |
| **原则沉淀** | 三条经验写进候选 project-structure.md：①目录结构=第一界面设计之初定死；②版本迭代必须人话 diff 放工作台；③用户工作面中文命名技术内部可英文 |

## 决策

- **为什么 references/agents 保留英文**：它们是 skill 技术内部，跟随 SKILL.md 的加载约定和将来 cskills 发布布局；用户工作面（顶层）已全中文。折中方案，用户已确认。
- **为什么 diff 放 `版本/版本说明.md` 而不是分散**：一个版本一节的集中说明，从 README 一眼链接，符合"人只看一个工作面"。

## 原则沉淀（写入候选 references）

这三条是本轮真实使用得到的后验，已写进 `版本/v0.0.3-候选/references/project-structure.md` 核心原则：

1. **目录结构是用户的第一界面** —— 设计之初定死，不边做边冒。
2. **版本迭代必须产出人话 diff** —— 旧版→新版→为什么→测试→证据，放工作台可见。
3. **用户工作面用项目语言命名**，技术内部按发布需要可保留英文。

> 这本身就是"用它迭代它自己"的实例：踩坑 → 总结经验 → 沉淀回方法，下一个用户不用重踩。
