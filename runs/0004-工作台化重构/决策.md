# 0004 · 工作台化重构 · 决策

> 把上次真实使用暴露的"信息架构反了"修掉：目标物和控制系统分家、可追溯被理解成多写文件、过早进入治理模式。这一代改的是**仓库怎么组织**，不是 SKILL.md 方法内容（候选 v0.1.0 仍等验收）。

## 触发：真实使用后的一条重要后验

第一次真正用 temper 迭代它自己，暴露了核心产品缺陷：

> **temper 会"管理一次迭代"，但不会"主持一次迭代"。**
> 机制层（state/Epoch/Evidence/Run）比用户工作面更完整；
> 一进来看到的全是内部术语，而"我正在炼的那个工件本身"不在工作台中央。

后验结论（写进 temper 的原则）：

> **被淬炼的工件是工作面的中心；元数据只能服务于工件变化，不能成为主要产物。**
> 可追溯 ≠ 文档越多越好；从 README 点一下就能顺着 当前版本 → Candidate → Diff → Run → 决策 找全，才是可追溯。
> 机制完整不等于好用；"打开目录三秒知道在改什么"是硬 Gate。

## 结构变化（目标物回到中央）

| 之前 | 现在 |
| --- | --- |
| SKILL.md 藏在 `~/.agents/skills/temper`，项目里只有指针 | 根目录 `SKILL.md` = 当前正式版，第一眼可见 |
| `方法/候选方法/` 藏候选 | `versions/v0.1.0-candidate/` 显眼 |
| 状态散在 README/循环/方法/项目定义/state.json 六处 | 人只看 README；后台只留 `.temper/state.json` |
| `循环/` `方法/` `项目定义/` 三个目录 | 删除，职责并入 README + VERSION.md + state.json |
| `运行记录/` | 改名 `runs/`（更短，`runs/NNN/` 每代一份） |
| 愿景基线对照表在 `评测/` | 移入 `runs/0002/`（每代记录自含尺子） |

## 对 temper 方法本身的后验（记入未来 SKILL.md 改进）

- SKILL.md 是给 AI 看的文档：专业、可执行，不做口语化（humanizer 用于给人看的 README/diff，不用于 SKILL.md）。
- 迭代项目布局：**工件在根目录，版本在 versions/，人只看 README，后台只有 state.json，每代只有 runs/NNN/**。这应成为 temper 默认的最小迭代结构（替代之前"标准形态"那套多目录）。
