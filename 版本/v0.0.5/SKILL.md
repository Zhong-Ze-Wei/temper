# 淬炼

把一个模糊想法或尚不稳定的 AI 任务，逐步变成可理解、可比较、可持续改进的工作系统。目标可能在探索中逐渐清楚；不同任务需要不同的反馈节奏、版本关系和人工参与方式，不要套用固定循环。

## 你只需要知道这四件事

当你把任务交给淬炼时，每一轮你只会看到四样东西，其余由它处理：

1. **现在发生了什么** —— 它先看了什么、发现了什么、当前判断是什么。
2. **这轮要解决什么** —— 当前真正缺的是业务理解、评测、数据、方法还是执行；这轮只做一件关键事。
3. **需要你做什么** —— 只有当它缺系统里不存在的信息、需要业务裁决、或判断方向时需要你。默认一轮找你 2 次（开始 + 结束）；异常情况会即时找你。
4. **结束后你会看到什么** —— 本轮结果、相对上一版的变化、证据能支持什么结论、下一步是什么。

你不需要先理解 Discovery、Epoch、Candidate、Baseline 这些概念。它们是你需要时才会展开的内部机制。

## 怎么开始

### 首次使用（三句话进入）

把当前任务和困扰直接说出来即可，例如：

> "我有一个法规资讯分析，现在能跑，但合并和影响分析不稳定。我不确定下一步该改 Prompt 还是先找业务定口径。"

淬炼会依次给你：

- **【判断】** 它先只读检查你的项目（README、定义、方法、评测、运行记录、近期 Git 变更），告诉你当前真正缺什么、值不值得继续迭代。**在你要求修改前，它只读不改。**
- **【计划】** 本轮只做一件关键事，并说明怎么做、证据能支持到什么程度。
- **【需要你】** 只有系统里没有、会改变方案的信息才会问你（例如业务口径、真实案例）。能自己读到的不会让你重复提供。

然后开始第一轮。

### 每一轮的工作方式

每轮固定四步，结果固定四样交付：

```text
① 只读看现状 → ② 只问必要问题 → ③ 跑一版并记录 → ④ 更新当前视图
```

**默认交付四样**：结果 / 相对上一版的差异 / 证据能支持什么 / 待你确认或下一步（探索期没有可比版本时，会直接说明，不硬凑差异）。

## 淬炼的职责边界（你在里面做什么）

| 淬炼自动处理 | 只在你介入时 |
| --- | --- |
| 读项目、找现状与冲突 | 业务事实与系统里不存在的信息 |
| 设计每轮最小改动 | 目标或定义变化 |
| 运行、做差异、找系统性问题 | 高风险判断或风险裁决 |
| 记录每代证据与决策 | 关键回归或方向争议 |
| 判断哪些能自动验证 | 是否采用新版本（工作/业务/生产） |

**它不会**：把你当成每轮结果的检查器；编造系统里没有的业务规则；在目标仍模糊时声称某一代客观更好；未经授权改动你的文件或对外发布（你已明确要求修改时不再重复索要许可）。

## 判断该不该用淬炼（Gate 前置）

开始前先快速回答一个问题：

> 下一次遇到同类任务，这次留下的证据是否会明显帮助结果更好？

- **会** → 继续，建立最小迭代结构。
- **不会 / 只是一次性或确定性任务** → 不建循环，直接完成任务或普通对话。

这个判断是首屏行为，不是埋藏的内部规则。它决定"要不要迭代"，与"用什么方法迭代"是两件事。

## 内部机制（按需展开，不阻塞首次体验）

以下是淬炼在后台使用的方法，你在需要理解"为什么"时可展开查看。用户不需要记住它们。

### 状态判断（决定"现在缺什么"）

主阶段决定缺什么：**Discovery**（目标仍模糊，先弄清问题）→ **Formation**（建最小可观察 V0）→ **Eval Building**（建立可信反馈）→ **Optimization**（稳定比较版本）→ **Stabilization**（生产级控制）。

循环强度决定要多少控制：**轻量 / 标准 / 严格**（高风险、不可逆、生产、强审计时至少严格）。

阶段、强度、策略、人机边界四个维度彼此独立，不混为一谈。详见 `references/assessment.md`。

### 策略选择（决定"怎样迭代"）

先判断版本关系：**替换 / 增量 / 并行 / 分流 / 实验 / 契约变化**（后三者不强制替换）。比较对象由关系决定：增量比较受影响 Case 并回归原路径；分流分场景评估；契约变化需 Epoch Review。详见 `references/strategy-selection.md`。

### 结构（决定"建多少"）

先复用现有文件，只补缺口；不建空目录；一个逻辑职责只保留一个当前权威来源。标准形态见 `references/project-structure.md`。简单任务只保留最简形态。

### 代际追溯（决定"每轮留什么"）

每代至少留下：目的 / 方法 / 产物位置 / 相对上一代的差异 / 评测与失败 / 决策与下一步。证据分级使用，不要求每代跑最贵的层。版本状态区分**当前工作 / 最近业务校准 / 生产**，不互相冒充。详见 `references/generation-traceability.md`。

### 用户面交互契约（这版新增）

首次进入与每轮交付的固定格式，见 `references/interaction-contract.md`。

## 版本边界

不建立常驻自动循环、复杂 Runtime、Hooks、多 Agent Graph、跨项目面板或外部执行 Backend；不自动发布。根据真实使用中出现的 failure mode 再增加能力。

### 持续逼近模式（v0.0.4 新增）

用户明确要求"持续迭代、逼近目的"时，可开启本模式（默认关闭）：

- **自主多轮**：AI 在授权范围内连续跑 看现状 → 定方向 → 改 → 验证 → 记录 → 小步晋升，不每代停下等人。
- **攒代汇报**：攒 2-3 代一次性向用户 review（每代仍有人话 diff），而不是每代都打断。
- **人工只在三处介入**：① 需要业务裁决时；② 目标/定义实质改变时；③ 攒代汇报点。低风险、可逆的改动自行完成。
- **边界**：只在授权范围内动（如仓库内），不碰全局环境、不发布，除非用户明确授权。

> 触发词：「持续迭代」「自动跑几轮」「攒着一起看」。默认仍走人机协同（每轮交付四样）。
