# 版本说明

> 每个版本改了什么，一眼看懂。这是"两版差异"的唯一入口；各代运行细节在 `迭代记录/`。

## 版本号规则

- **小步进**：每改一点 +0.0.x（0.0.2 → 0.0.3 → …），不搞大跳。
- **唯一版本号**：SKILL.md frontmatter 的 `version` 字段。
- 版本只反映"改到哪了"，不承诺外部发布。本仓库是试验田，不主动同步 GitHub / CSkills / 安装位置。

## 当前版本状态

| 版本 | 是什么 | 状态 |
| --- | --- | --- |
| **v0.0.1** | 初版，概念手册形态 | 历史快照（`版本/v0.0.1/`） |
| **v0.0.2** | 概念手册形态（内容同 v0.0.1），版本号对齐注册表 0.0.2 既有记录 | 历史（快照见 `版本/v0.0.2-历史/`） |
| **v0.0.3** | 用户体验层重构 + 工作台化 + 三条原则沉淀 | **当前正式版**（根 SKILL.md，已采纳） |

> 说明：v0.0.2 → v0.0.3 的完整人话 diff 见下方章节。v0.0.3 已仓库内晋升，**未同步**安装位置 `~/.agents/skills/temper` 与注册表（试验田纪律）。

## 版本怎么升

- **任何改动**（行为、文案、机制微调）→ 小步进 +0.0.x
- **"什么叫做好"变了** → 契约级变化，记一次 Epoch Review，版本仍小步进
- 不搞 0.1.0 这种大跳，除非明确到了"方向级重做"

## 怎么发一版（试验田纪律：不主动同步）

```text
改 版本/<新版本>/ 里的 SKILL.md（或根 SKILL.md）
  → 验收
  → 同步到安装位置 ~/.agents/skills/temper
  → cskills publish <含 SKILL.md 的目录>  （发到注册表）
  → cskills sync                        （拉回，保持两边一致）
```

发布是**外发动作**，必须你点头才做。本地仓库只是试验田，**不主动**同步 GitHub / CSkills / 安装位置。

## 两个"temper"别搞混

| | 位置 | 角色 | 能不能直接改 |
| --- | --- | --- | --- |
| 权威副本 | 根 `SKILL.md` + `版本/` | 项目里被迭代的工件 | **能** |
| 部署副本 | `~/.agents/skills/temper` | 各会话实际加载 | **别改**（会被 cskills 覆盖） |

## v0.0.2 → v0.0.3 改了什么

### 一句话

**从"概念手册"变成"带着用户做"**：用户不再需要先学 Discovery、Epoch、Candidate 这些术语，打开就能知道现在在改什么、要不要自己、下一步去哪。

### 旧版（v0.0.2）是什么

- 开篇是"核心原则 + 工作方式 1-6"，需要用户先理解内部流程才能配合。
- 首屏直接输出诊断卡（阶段/强度/策略/版本关系），概念直接暴露。
- 用户面对话无固定契约；没有"该不该用 temper"的前置判断。
- 结构是抽象的"逻辑职责"描述，没有给出具体目录形态。

### 新版（v0.0.3）改了什么

| 改动 | 旧版 | 新版 |
| --- | --- | --- |
| 首屏 | 概念手册（工作方式 1-6） | "你只需要知道四件事"（现在什么情况/这轮干嘛/要不要你/做完看到什么） |
| 概念暴露 | 直接输出诊断卡 | 沉到"内部机制（按需展开）"，不阻塞首次体验 |
| 首次对话 | 无固定格式 | 三件套【判断】【计划】【需要你】 |
| 每轮交付 | 无约定 | 默认四样：结果/差异/证据/待你确认 |
| Gate 前置 | 只藏在 references | 首屏"该不该用淬炼"一句话判断 |
| 人机分工 | references 有支撑 | 职责边界表显式化 |
| 打扰节奏 | 无 | 默认一轮 2 次（开始+结束），异常即时 |
| 交互契约细节 | 无 | 新增 `references/interaction-contract.md` |
| 结构规范 | 抽象职责 | 工件中心工作台（README + 版本/ + 迭代记录/ + state.json） |

### 为什么改（依据）

- 真实使用（第一轮自举）暴露：temper 会"管理一次迭代"但不会"主持一次迭代"，机制层比用户工作面完整，一进来全是内部术语。
- 设计文档（设计资料/04）本就要求：复杂度在后台、行动在前台、progressive disclosure。
- codex 独立评审确认方向对，并修正了三类问题（结构规范冲突、指针漂移、契约过硬）。

### 测试验证了什么（评测/测试任务集.md）

三个真实任务 A/B/C 全通过：

- **A 客服分类**：正常优化闭环成立（V0→diff→最小修改→复验→诚实边界）。
- **B 新增客户口径**：识别出缺的是业务口径不是代码，克制住不改代码不造评测。
- **C 报销流程**：进入 Discovery，克制住不给自动化方案，暴露未知。

三个任务里，术语（Discovery/Epoch/Candidate）只出现在内部推理，**没有暴露给用户** —— 证明"内部机制按需展开"真实生效。

### 证据能支持到什么

- ✅ 用户体验层重构方向正确，三个真实任务里行为符合愿景。
- ✅ 首次交互不再吓退用户。
- ⚠️ 仍缺：真实长周期使用反馈（生产反馈层）；interaction-contract 的"默认 2 次打扰"在复杂任务里是否够用。
