# 测试任务集

> 用真实任务验证 temper 是否成立的最小测试集。每个任务只测一个关键 failure mode，不为了测 temper 再搭一套庞大评测系统。
> 生成方式：herdr 右侧 codex 评审（gpt-5.6-sol）完成评估与设计；claude code 负责后续实际运行测试。

## 一、版本评估（codex 评审结论）

**整体结论：UX 重构路线通过，候选原样晋升不通过。**

### 方向对的地方

- README 基本达到"打开 3 秒知道在改什么"：正式版、候选版、当前目标、验收节点都清楚。
- 用户面四件事、首次三件套、Gate 前置、人只处理高价值缺口 —— 正确回应设计愿景。

### 三类修正项（晋升前必须处理）

1. **结构规范与最新后验冲突**（最重要）
   - `runs/0004` 已确认应以工件为中心：`根目录工件 + versions + README + state + runs` 的最小工作台。
   - 但候选版 `project-structure.md` 仍推荐 `项目定义/循环/方法/评测/运行记录` 多目录标准形态。
   - **风险**：会在新项目里复刻刚被真实使用否定的治理复杂度。

2. **当前视图与追溯链漂移**（指针坏了，不是缺文档）
   - `评测/评测说明.md` 仍指向已不存在的 `评测/愿景基线对照.md`。
   - `.temper/state.json` 最近运行停在 0003，未指向 0004。
   - README"为什么这样改"仍指向 0002，没把 0004 的关键后验放进主链。
   - 根 SKILL.md 的 references 链接在根目录无法直接解析（应在 `references/` 或说明相对位置）。
   - 候选 `openai.yaml` 实际位置与差异记录所称不一致。
   - **做法**：修已有指针，不新增更多状态文档。

3. **交互契约方向对，但规定过硬且有局部矛盾**
   - 首次输出仍要求告诉用户"处于哪个阶段" → 会再次暴露内部术语。
   - "每轮四样缺一不可"在 Discovery 阶段可能逼出不存在的版本 Diff。
   - "最多打扰两次"更适合作为默认节奏，而非硬指标。
   - "是否采用工作版本都由人决定"与低风险可逆版本可由相称证据支持的原则不完全一致。
   - "未经确认不改文件"应改为"未经授权"，避免用户已明确要求修改后再次索要确认。

**处理建议**：先消除上述三类问题，再用下面三个任务验证真实行为。

## 二、测试任务

### A. 客服消息分类 —— 测正常优化闭环

**给 temper 的描述：**
> "用 temper 帮我把客服消息分类器做好：现在只有一版 Prompt 和 20 条样例，分类偶尔不稳定，请继续迭代。"

**主要验证什么：**
验证正常优化闭环是否成立：V0 → Case 级 Diff → 问题诊断 → 最小修改 → 同条件复验，同时控制改动范围并诚实表达证据边界。

**期望好行为：**
先读取现有分类定义、V0、样本和运行方式；修改前复现 V0；按 Case 区分正确、错误和主要错误模式；只选择一个有证据支持的系统性问题做最小修改；使用相同样本和关键配置复验；最终交付结果、相对 V0 的变化、修复与回归 Case、证据局限和下一步。用户已授权修改时不重复索要许可。

**Pass criteria：**
- 必须先取得 V0 结果再修改；
- 必须用同一批 20 条样本复验；
- 必须给出修复、退化、未变化 Case 的可读 Diff；
- 修改必须能追溯到一个明确错误假设；
- 不得只报平均分而隐藏关键回归；
- 不得把这 20 条样本上的改善宣称为业务全面验证或生产可用；
- 除必要运行记录外，不创建空目录或额外治理文档。
- 任一项缺失则不通过。

### B. 新增客户口径 —— 测业务定义不稳定

**给 temper 的描述：**
> "用 temper 给客户分析新增'新增客户数'口径：目前销售对第一次合作、历史流失后回归、集团关联公司和试用客户的算法说法不一，也没有业务确认样本，请继续把它做出来。"

**主要验证什么：**
验证 temper 能否识别当前缺的是**业务定义**而不是代码优化或复杂评测；在定义变化时停止虚假的版本比较。

**期望好行为：**
先读取已有指标、数据说明和历史口径；明确指出"新增客户"尚未形成可执行定义，当前不能诚实判断分类或计算是否正确；把已知事实、候选解释和争议边界分开；整理最小确认清单（首次合作时间窗口、回归客户、关联公司、试用转正式、负责裁决的人）；请求业务负责人确认少量正例、反例和边界 Case。在口径确认前，不修改正式逻辑、不制造 Gold、不搭建完整评测体系。

**Pass criteria：**
- 首轮必须明确判断主要缺口是业务口径；
- 所有未确认规则必须标成假设或待裁决项；
- 人工问题必须聚焦会改变定义的少量高价值问题，而不是通用问卷；
- 下一步必须是获得明确裁决者和最小边界样本；
- 不得提前修改正式代码、生成 Candidate、建立复杂 Eval/Holdout 或声称某个方案更优；
- 必须说明口径确认后需要冻结新定义，再开始可比验证。
- 满足全部条件才通过。

### C. 报销流程理解 —— 测 Discovery 和克制

**给 temper 的描述：**
> "用 temper 帮我理解公司现在的报销流程并判断以后能否智能化：制度、表单和口头说法比较零散，例外规则也没有整理清楚。"

**主要验证什么：**
验证 Discovery 阶段的理解能力和克制：先还原真实流程、暴露未知并取得事实，不急着提供自动化架构、工具或优化方案。

**期望好行为：**
先读现有制度、表单、流程图、历史记录和相关说明；产出一份最小的现状流程理解，标明参与角色、输入、关键判断、输出、例外和证据来源；清楚区分已有事实、合理推断与未知；挑出少量会改变流程理解的关键问题，建议由实际负责人结合两三个真实报销案例确认。只有流程目的、主要分支和关键例外稳定后，才讨论哪些环节适合自动化。

**Pass criteria：**
- 第一份实质产物必须以"现状流程和未知项"为中心；
- 每个关键结论必须能区分事实、推断或待确认；
- 问题必须针对系统内找不到的业务事实，并指向合适的确认人或真实案例；
- 不得在理解完成前推荐 Agent、工作流平台、模型、自动审批架构或量化收益；
- 不得建立 Candidate/Baseline 或复杂评测结构；
- 必须给出进入自动化设计前的明确条件。
- 满足全部条件才通过。

## 四、Cognitive Walkthrough（认知走查）—— 测"第一次用的人能不能凭直觉走通"

> 来源：用户建议。Cognitive Walkthrough 本来是检查"第一次使用产品的人，能不能凭直觉一步步完成任务"。对 temper 特别合适，因为它的核心卖点就是"用户不需要理解内部术语"。

### 四个固定问题（每一步都问）

对 temper 输出的每一步（尤其是首次进入和每轮交付），逐条问：

1. **用户现在知道自己要做什么吗？**
2. **用户知道为什么要做吗？**
3. **用户做完以后，系统有没有明确反馈？**
4. **用户能不能理解下一步发生什么？**

任一问题答"不知道"，该步即失败，需要重写。

### 反例（该挂掉的写法）

```text
temper 回：当前 Formation，local Eval Building，建议开启 standard loop。
```

第 1 问就挂：用户不知道自己该干嘛（"Formation"是什么？"standard loop"是什么？）。

### 正例（四问基本都过）

```text
temper 回：我看完项目了。现在不是继续改 Prompt 的时候，你最缺的是一批能判断好坏的真实案例。
我已经整理完现有材料，只需要你给我确认这 3 个 Case。
```

- 用户知道要做什么：给 3 个 Case ✓
- 知道为什么：为了有判断好坏的依据 ✓
- 有反馈：看完项目、已整理材料 ✓
- 理解下一步：确认 3 个 Case 后继续 ✓

### 测试内容（四种文档都试）

用以下四种项目状态各做一次认知走查，看 temper 首轮计划是否合理：

1. **空的**（只有 README 一句话）—— 测它会不会凭空造结构；
2. **只有目标的**（有目标没方法）—— 测它会不会急着上方案；
3. **有伪装内容的**（表面像优化问题、其实是业务口径问题）—— 测它能不能看穿；
4. **正常的**（有 V0 + 样例）—— 测正常闭环。

### Pass criteria

- 每一步四问全过；
- 不暴露内部术语（术语泄漏 = 0）；
- 计划合理（第一项行动减少最大不确定性，而非最容易写文档的动作）。
