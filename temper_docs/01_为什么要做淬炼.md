# 为什么要做「淬炼」

## 问题不是“第一版做不出来”

AI 时代，一个任务第一次跑起来越来越容易。

Prompt 可以快速生成，代码可以让 Agent 写，脚本、接口、数据处理也都能很快搭出 V0。

真正困难的，往往是 V0 之后：

- 这一版到底哪里错了；
- 是 Prompt 的问题，还是业务定义本来就没想清楚；
- 是取数逻辑错了，还是数据源本身就不稳定；
- 是某个 Case 偶然失败，还是方法存在系统性问题；
- 新版本看起来更好，到底是真的更好，还是只是换了表达；
- 业务后来改了口径，旧版本和新版本还能不能直接比较；
- 哪些结论只是 AI 的猜测，哪些已经有证据；
- 哪些地方 AI 可以继续自己跑，哪些地方必须找人；
- 项目积累了大量 Markdown、运行结果、复盘以后，到底哪个才是当前有效状态。

很多团队现在解决这些问题的方法仍然是：

```text
跑一版
→ 看哪里不满意
→ 改一点
→ 再跑
→ 再看
→ 继续改
```

每一步都合理，但跑到第五版、第十版之后，很容易失去三个东西：

1. **为什么改；**
2. **凭什么说变好了；**
3. **现在到底以哪一版、哪套定义为准。**

这就是「淬炼」最初要解决的问题。

---

## AI 带来的变化：实验越来越便宜，验证和理解反而成为瓶颈

过去执行昂贵，所以工作方式天然强调：

> 先尽量想清楚，再开始做。

现在很多数字化工作发生了变化。

改 Prompt、改一段代码、重新跑一批数据、生成一个 Candidate，成本已经非常低。

因此工作的瓶颈正在从：

> “能不能做出来”

转向：

> “怎么知道哪里不对，以及下一轮应该改什么”。

所以真正值得工程化的，不再只是执行过程，而是：

```text
运行
→ 观察
→ 获得证据
→ 判断问题
→ 修改
→ 再验证
```

也就是说，我们需要的不是一个“永远第一次就做对”的系统，而是一个：

> **即使第一版并不完美，也能够持续发现错误、获得反馈、修正自己并且不丢失历史依据的系统。**

---

## 真实工作并不总是“优化已有方法”

更重要的是，很多任务一开始连“正确答案是什么”都不完全明确。

例如数据分析：

- 业务自己还没理顺取数逻辑；
- 分析人员先做一个统一口径；
- 指标体系也是先自己拆出来；
- 做着做着发现数据不对，再查来源；
- 口径不确定，就继续验证数据结构和业务逻辑；
- 最后拉业务开会，由真正熟悉流程的人判断是否符合管理需求。

这里被改变的并不只是 SQL。

可能同时在变化：

```text
对业务的理解
→ 指标定义
→ 数据口径
→ 取数逻辑
→ 最终产物
```

因此我们不能把所有问题都粗暴理解成：

> “已经有一个正确目标，现在只需要优化 Prompt。”

「淬炼」需要支持的是更完整的过程：

```text
模糊问题
→ 建立当前理解
→ 做出最小产物
→ 暴露未知
→ 获得真实反馈
→ 更新问题理解
→ 方法逐渐稳定
→ 才进入可信的版本比较
```

---

## 最终要解决的不是 Loop，而是“任务如何成熟”

所以我们做「淬炼」，不是因为“Loop 很酷”。

真正的问题是：

> **一个原本只能靠某个人脑子持续维护的任务，怎么逐渐变成一个目标更清楚、变化有依据、版本可比较、人的介入有理由、别人也能接手的系统。**

Loop 只是其中一种实现方式。

真正的产品对象是：

> **任务从模糊、能跑、不稳定，到稳定可用的成熟过程。**
