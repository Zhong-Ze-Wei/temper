# 最小项目结构

结构的目标是让用户看得懂当前任务并支持可靠迭代，不是让所有项目长得一样。**先让"正在被淬炼的工件"站在工作台中央**，再按真实需求补最小结构。元数据只服务于工件变化，不能成为主要产物。

## 核心原则（来自真实使用后验）

- **工件在中央**：被迭代的东西（SKILL.md、方法、Prompt、算法）放在根目录或最显眼处，不是藏在指针后面。
- **人只看一个工作面**：README 是唯一工作台第一屏；后台只留 `.temper/state.json`。不要让人在六个地方理解"现在发生了什么"。
- **可追溯 ≠ 文档多**：从 README 顺着"当前版本 → Candidate → Diff → Run → 决策"能一路找全，就是可追溯。状态不要拆到多个目录重复表达。
- **复杂度必须解决问题**：只有真实需要时才增加控制；刚启动就铺满治理目录，等于没理解问题。
- **目录结构是用户的第一界面**：用户最先体验的就是目录长什么样，所以**设计之初就定死**，不要边做边冒新目录。它决定后面所有东西（diff、版本、文档）长在什么上面。
- **版本迭代必须产出人话 diff**：每次版本升级，必须有"旧版是什么 → 新版改了什么 → 为什么改 → 测试验证了什么 → 证据能支持到什么"的说明，并放在工作台（README）一眼可见。不要只留文件级 diff。
- **用户工作面用项目语言命名，技术内部按需保留英文**：用户会看到的顶层目录用中文（或项目语言）；references/agents 等技术内部按发布需要可保留英文。发布时再映射到平台布局，不要为了发布让用户天天面对英文目录。

## 逻辑职责

按项目需要识别以下角色：

- **工件**：正在被迭代的对象（当前版本 + 候选版本）；
- **定义**：当前目的、边界、成功标准和未知项；
- **状态**：阶段、版本关系、当前节点和下一步；
- **评测**：评测口径、样本、结果和测试集；
- **运行**：每一代的输入、产物、Diff 和决策；
- **版本**：各版本快照与时间线。

## 创建规则

遵循：复用现有文件 → 补充现有文件 → 必要时拆分 → 最后才新建。

- 不创建空目录或占位文档；在第一次实际需要内容时创建。
- 一个逻辑职责只保留一个当前权威来源；README 是视图，不是重复事实源。
- 候选版本与当前版本分开，决策前不原地覆盖。
- 运行产物和决策记录原则上不可变；更正时追加说明或生成新一代。
- 新文件应从 README 可发现；不要制造孤儿文档。
- 修已有指针优先于新增状态文档。

## 默认最小形态（工作台优先）

这是真实使用验证过的形态。仅当项目没有等价结构时使用这些默认名称。

### 最简单（探索 / 轻量）

```text
README.md                    # 工作台第一屏
<工件>                        # 正在迭代的对象，放根目录
.temper/
    state.json               # 后台机器状态
```

### 标准（要版本比较）

这是真实使用验证过的**工件中心工作台**形态（本仓库即此形态）：

```text
README.md                    # 工作台第一屏：当前版本 / 候选版本 / 现在在哪一步 / 这版改了啥
<工件>                        # 当前版本，根目录
版本/
    版本说明.md               # ★每版改了什么（人话 diff）+ 版本时间线 + 发布链
    <v0.0.1>/                # 版本快照（每版一份）
    <v0.0.2-候选>/           # 候选（仅在替换式迭代需要时）
迭代记录/
    <run-id>/                # 每代一份：diff / 决策 / 评测
    汇报.md                  # 持续逼近模式下的攒代汇报（可选）
评测/
    评测说明.md               # 尺子；测试集可放这里或单独
.temper/
    state.json               # 后台机器状态
```

**命名约定**：用户工作面（顶层目录、文档名）用项目语言命名（如中文）；技术内部（references/agents 等）按发布需要可保留英文。目录名用 `<...>` 时表示"按你的工件命名"，不是字面。

**对比旧的"多目录标准形态"（不再推荐）**：之前用 `项目定义/ 循环/ 方法/ 评测/ 运行记录/` 五个目录承载状态，真实使用后发现它把工件藏到了指针后面，人打开目录不知道在改什么。现在收敛为 **README + 版本/ + 迭代记录/ + state.json** 四件套，工件在根目录。

**一致性规则**：方法文档里的默认形态必须与真实项目实际形态一致；若项目演化出了更好的形态，先改文档再引用，不要文档一套、项目一套。

### 严格控制

从标准形态按已识别风险增加所需内容，例如关键基准、人工裁决、风险与回滚说明。不要一次创建 Anchor、Holdout、Hooks、Runtime、Graph 等所有目录。

## `.temper/state.json`

这是轻量机器状态和路径映射，不保存重复的完整业务定义。建议包含：

```json
{
  "schema_version": 1,
  "stage": "discovery",
  "intensity": "light",
  "strategy": {
    "change_relation": "exploration",
    "feedback_cadence": "per_generation_observation",
    "human_mode": "review_each_round"
  },
  "comparison_status": "exploratory",
  "epoch": null,
  "versions": {
    "working": "SKILL.md",
    "candidate": "版本/v0.0.2-候选",
    "last_business_validated": null,
    "production": null,
    "active_experiments": []
  },
  "current_step": "frame-first-v0",
  "paths": {
    "working_skill": "SKILL.md",
    "version_hist": "版本/版本说明.md",
    "runs": "迭代记录"
  },
  "last_run": null,
  "next_action": "生成第一个可观察产物",
  "human_attention": []
}
```

根据阶段只保留有意义的字段。业务内容仍以用户可见文件为准。

## 当前状态视图（在 README 第一屏）

用户应能快速看到：

- 当前正式版、当前候选版、当前目标、现在在哪一步；
- 这版主要改了什么；
- 入口：当前工件 / 新版 / 两版差异 / 为什么这样改。

只有需要追根问底时才展开后台概念（阶段、强度、Epoch、证据等级）。
