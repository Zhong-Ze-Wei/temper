# 代际比较与追溯

每一代都要留下足够信息，使人能够理解发生了什么、为什么修改、结果如何以及接下来怎么决定。自动化程度可以降低人工关注频率，但不能减少可观察性。

## 代际性质与版本关系

### 探索轮次

用于目标或边界仍模糊的 Discovery。比较重点是：

- 产生了什么新事实；
- 哪个假设得到支持或被推翻；
- 用户真正关心的标准是否更清楚；
- 下一轮要验证什么。

探索轮次可以比较产物差异，但不要在成功标准变化的情况下宣称某代性能更优。

### 正式变化

用于目标和评测已足够稳定的 Epoch。先记录它是替换、增量、并行、分流还是实验，再选择参照物和比较范围。只有替换式变化才默认使用 Candidate 对当前工作版本；增量变化重点检查新增能力及未受影响部分的回归。

契约变化不是普通一代。进入 Epoch Review，明确哪些历史结果仍可比较。

## 比较链

保持以下链路可追溯：

```text
当前定义或 Epoch Contract
→ 方法版本
→ Run Manifest
→ 产物
→ Diff / Eval
→ Evidence
→ 决策
→ 适用的版本状态指针
```

任一环节可以是项目已有文件或外部系统，但记录中必须能定位。

## 每一代的最小记录

实际运行时创建独立记录，不覆盖上一代。默认可采用：

```text
运行记录/<run-id>/
    manifest.json
    产物/                    # 或指向已有产物位置
    版本差异.md
    评测结果.md              # 有正式评测时
    决策.md
```

只创建本代实际有内容的文件；小型任务可以把差异、评测和决策合并为一个 Markdown。

Manifest 至少记录适用项：

- `run_id`、时间和任务标识；
- 当前 stage、intensity、comparison status 和 Epoch；
- 本代目的或待验证假设；
- 版本关系、参照版本、变更版本、方法版本或内容哈希；
- 当前工作版本、最近业务校准版本和生产版本中适用的指针；
- 输入、样本、Gold/Eval 版本；
- 本代使用的证据层级和下一检查点；
- 模型、关键配置和环境差异；
- 产物、Trace、评测和决策文件路径；
- 运行状态和异常。

不要把密钥或敏感运行数据写入 Manifest。

## 人工可读 Diff

`版本差异.md` 应帮助人做决定，而不只是重复文件级 Diff。按实际情况回答：

- 本代改变了什么；
- 哪些 Case 变好、变差或只是表达不同；
- 是否出现新的关键错误；
- 哪些变化无法可靠判断；
- 是否支持原假设；
- 建议人工重点查看什么；
- 当前证据支持工作采用、业务校准、生产发布中的哪一种判断。

尽量链接具体 Case、原始依据和产物。不要用笼统总结代替证据。

## 证据类型

保持最小但清晰的区分：

- **Observation**：观察到的现象；
- **Evidence**：可验证并可追溯的事实；
- **Hypothesis**：关于原因的解释；
- **Intervention**：为验证假设实施的修改；
- **Evaluation**：修改后的比较结果；
- **Validated Learning**：由结果支持、适用边界清楚的经验。

一次复盘中的猜测不能直接成为稳定经验。Validated Learning 应指向支持它的运行和 Evidence。

## 证据梯度与反馈节奏

证据可以分层使用，不要求每代都执行最昂贵的一层：

1. 运行有效性：结构、Schema、测试、完整性和错误检查；
2. 固定案例回归：关键 Case、规则和不变量；
3. 差异复核：人工或可追溯的自动对比；
4. 专家抽查：对高价值、低置信度或争议 Case 裁决；
5. 业务 Gold：按正式口径标注或验收；
6. 生产反馈：真实使用结果、事故、申诉或业务指标。

低层证据可以支持继续试验或可逆的工作采用，但不能冒充高层结论。Gold 成本高时，允许多代共享一个业务校准周期；每代仍记录便宜证据，达到约定检查点后集中打标。

检查点不要只写死“每 N 代”。可以由以下一种或组合触发：累计有效改动、核心语义或契约变化、关键回归、方向争议、准备发布、运行量达到阈值、到达时间周期或用户明确要求。

## 版本状态

按项目实际情况区分：

- **当前工作版本**：后续迭代默认从它继续，可由与风险相称的便宜证据支持；
- **最近业务校准版本**：最近一次经过业务 Gold 或等价高可信反馈确认的版本；
- **生产版本**：当前对外运行的版本，需要发布与回滚要求支持；
- **实验或并行版本**：仍在比较、仅服务特定场景或不准备替换其它版本。

这些指针可以相同，也可以不同。更新其中一个不自动更新其它指针，不把“工作采用”写成“业务已验证”。

## 可比性检查

在声称性能优劣前确认：

- 属于同一 Epoch；
- Goal、Definition、Metric 语义和关键边界未实质改变；
- 使用相同证据依据，或差异已明确并限制结论范围；
- 输入分布和运行条件足够可比；
- 结构校验与业务质量没有混为一谈。

如果尺子改变，标记 `epoch_review_required`，不要将分数直接连成趋势。

## 状态变更与 Promotion

任何状态变更前先说明要变更的是工作、业务校准还是生产指针。

采用为当前工作版本前至少确认：

- 运行和产物有效；
- 现有证据与声明范围相称；
- 没有不可接受的关键回归；
- 结论能追溯到 Diff 和 Evidence；
- 该变化可逆，或已满足风险所需的人工确认与回滚要求。

标记为业务已校准时，必须有业务 Gold、明确裁决者或事先接受的等价高可信反馈。进入生产还要满足项目自己的发布、权限、监控和回滚要求。

决策使用与项目语言一致的明确状态，例如：`adopted_as_working`、`kept_parallel`、`experiment_only`、`needs_more_evidence`、`business_validated`、`released`、`rejected` 或 `epoch_review_required`。不要强迫已有项目改枚举。V0.1 不自动修改 Gold，不自动更新任何版本指针。

## 一轮结束

更新当前状态中的最近运行、版本关系、证据等级、决策、适用指针、人工待办和下一检查点。若本代发现目标、定义或评测尺子需要实质变化，停止普通优化并进入 Epoch Review。
