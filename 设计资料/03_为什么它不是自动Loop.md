# 为什么「淬炼」不是一个自动 Loop

## Loop 很重要，但它不是产品本身

最容易犯的错误是把「淬炼」理解成：

> AI 自动生成 Candidate → 自动 Eval → 自动修改 → 无限循环。

这只适用于一部分已经成熟的任务。

真实工作里，任务可能处于完全不同的状态。

---

## 有时候应该迭代方法

例如：

- Goal 已经明确；
- Eval 比较可靠；
- 输入和输出边界稳定；
- 错误可以被自动判断。

这时可以使用成熟循环：

```text
当前版本
→ Candidate
→ Run
→ Eval / Diff
→ Diagnose
→ Change
→ Regression
→ Promotion
```

这里真正被优化的是“怎么做”。

---

## 有时候应该先迭代对问题的理解

例如：

业务还没把流程理清楚。

此时最错误的动作是让 AI：

> 自动优化流程。

因为系统甚至不知道：

> 为什么流程现在是这样。

正确循环反而可能是：

```text
当前理解
→ 收集真实案例
→ 标出未知
→ 找负责人确认
→ 更新理解
→ 再画流程
```

此时产出的价值不是“性能提升”，而是：

> 我们对问题认识得更准确了。

---

## 有时候迭代的是指标和定义

例如数据分析人员先自己拆一个指标体系。

这个指标体系可能只是：

> 当前最合理的候选定义。

随着真实业务反馈进入：

- 某个指标被证明没有管理意义；
- 某个口径应该拆分；
- 某个数据源无法支撑原有假设。

那么下一轮修改的不是“取数算法”，而可能是 Definition 本身。

---

## 有时候根本不该继续 Loop

如果：

- 没有真实反馈；
- AI 无法判断对错；
- 人也没有新的信息可以提供；
- 当前任务只是一次性工作；
- 改进收益小于维护系统的成本；

正确动作可能就是：

> 停止系统化，直接人工完成。

所以「淬炼」必须具备一个能力：

> **判断当前到底有没有资格、有没有必要进入迭代。**

---

## 三个维度不能混为一谈

### 当前阶段

回答：

> 现在最缺的是什么？

例如：

- Discovery：先搞清问题；
- Formation：先做出能观察的 V0；
- Eval Building：先建立可靠反馈；
- Optimization：可以正式比较版本；
- Stabilization：需要生产级控制。

### 控制强度

回答：

> 这件事需要多少风险控制？

例如：

- 轻量；
- 标准；
- 严格。

### 人的参与方式

回答：

> 这一轮人和 AI 怎么分工？

例如：

- 人工主导；
- 人机协同；
- 自动迭代。

三个维度是正交的。

因此可以存在：

```text
严格 + 高度自动运行 + 人工 Promotion
```

也可以存在：

```text
轻量 + 人工主导
```

---

## 最核心的一句话

> **「淬炼」不是帮所有任务自动循环，而是判断“当前到底什么东西值得被循环”，再生成合适的反馈结构。**

这也是它与普通 Workflow / Agent Loop 最大的区别。
