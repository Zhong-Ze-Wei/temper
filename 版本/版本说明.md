# 版本说明

> 每个版本改了什么，一眼看懂。这是"两版差异"的唯一入口；各代运行细节在 `迭代记录/`。

## 版本号规则

- **小步进**：每改一点 +0.0.x（0.0.2 → 0.0.3 → …），不搞大跳。
- **唯一版本号**：SKILL.md frontmatter 的 `version` 字段。
- **代数以 `迭代记录/` 目录为准**；commit 前缀只是提示，不构成代号。
- 版本只反映"改到哪了"，不承诺外部发布。本仓库是试验田，不主动同步 GitHub / CSkills / 安装位置。

### 一句话

### 改了什么

- `references/project-structure.md` 标准形态示例改为**真实验证过的中文工作台形态**（版本/ + 版本说明.md + 迭代记录/ + state.json）。

- README 目录导航修正残留的"v0.0.3-候选"。

### 证据

- 一致性修正：方法示例 = 真实仓库形态（本仓库即活例）。
- 这是文档/示例修正，不改行为，风险低。

## v0.0.6 → v0.0.7 改了什么

### 一句话

**temper 现在会自动载入新的评测基准，而不是等用户问"你载入没有"。**

### 为什么改

用户发现 Cognitive Walkthrough 被加进了测试集文档，但 temper 自己"不会自动载入它"。根因：temper 知道"要评测"，但不知道"评测基准本身是活的、要被迭代的"。

### 改了什么

- `SKILL.md` 新增"评测自动载入"机制：每次迭代把评测当被测对象，遇到新的可判定标准 → 判断有效性（可判定/覆盖盲区/证据可标注）→ 有效则纳入测试集、无效则说明原因。
- `评测/评测说明.md` 重写为完整评测体系（愿景对照 + 真实反馈 + 行为测试集 + 认知走查四维），并明确"评测自动载入"是机制而非约定。

### 验证 / 证据

- 机制性改动：加能力，不改既有行为。
- 直接解决了用户指出的 failure mode：新评测基准（如 CW）会被自动识别并纳入，而非依赖用户提醒。
- ⚠️ 尚未验证"它真的会自动载入"——需要一个新评测标准来测这条机制本身。

## v0.0.7 → v0.0.8 改了什么

### 一句话

**评测自动载入从"AI 自己判断就写"升级为"静态文件更新"：触发 → 问用户 → 确认才改。**

### 为什么改

用户指出：更新测试集/评测说明这类"单一权威文件"会改变后续所有轮的参照，属于受控动作，不该默默做，应该触发 + 问用户。"评测体系本身要被迭代"这个元认知也要写进 temper。

### 改了什么

- `SKILL.md` 把 v0.0.7 的"评测自动载入"升级为"静态文件更新"机制：
  - 定义哪些是"单一权威文件"（评测/README/state/版本说明/方法本体）；
  - 触发条件（新评测标准 / 文件脱节 / 用户说"这该沉淀"）；
  - **触发后必须问用户**（目标文件 + 建议更新 + 影响），确认才写；
  - 明确"评测自动载入是静态文件更新的一种"。
- `评测/评测说明.md` 同步：评测载入 = 受控动作，非自动写文件。

### 验证 / 证据

- 机制性改动：把"默默写"改为"提议 + 确认"。
- 直接修掉 v0.0.7 的缺陷（自己判断有效就写，未过用户）。
- ⚠️ 尚未用真实"新评测标准"验证完整链路（触发 → 问用户 → 确认）——需要一次真实触发来测。

## 版本怎么升

- **任何改动**（行为、文案、机制微调）→ 小步进 +0.0.x
- **纯验证代不升版本号**：只跑验证、不改行为的代，记入迭代记录即可，不占版本位（v0.0.6 曾违反此规则）
- **"什么叫做好"变了** → 契约级变化，版本仍小步进
- 不搞 0.1.0 这种大跳，除非明确到了"方向级重做"（0.0.8 → 0.1.0 即一次：依据为两组独立审查收敛 + 用户裁决）

## 怎么发一版（同步方法见根目录《发布与同步》）

三个任务里，术语（Discovery/Epoch/Candidate）只出现在内部推理，**没有暴露给用户** —— 证明"内部机制按需展开"真实生效。

## 历史待办（v0.0.3 时期；三条规则当时已沉淀进 references，0.1.0 起由 SKILL.md"版本纪律"章节承载）

这次踩的坑表明 temper 缺三条硬规则（应写进候选 v0.0.3 的 references）：

1. **目录结构是用户体验第一界面，设计之初就定死**，且默认用项目语言命名用户工作面。
